# Workbench 收尾代码审查（2026-11-22）

## 结论

代码本身已经达到发布候选状态：全量静态检查、单测、构建都通过，没有发现阻断启动或数据损坏的缺陷。真正需要收尾的不是“再写功能”，而是**把最新代码重新打成安装包、把版本/签名/推送三个发布动作闭环**。

本次审查顺手修了 4 个会影响真实使用的问题，并补了回归测试：

1. **助手误创建任务**：`create_task` 原来只匹配“任务 + 新建/创建”，于是“我上周新建了一个任务”“怎么新建任务？”也会被当成写指令。写入开关打开时，这会往真实任务表里落一条假任务。现在要求祈使/请求语气，并排除过去时、疑问和教程式表达。
2. **成本卡币种错误**：成本库全程按 USD 记账，助手工具卡却写成“本月 ¥12.34”。现在统一走 `formatUsd`，并加了“不出现 ¥”的测试。
3. **助手 HTTP 客户端跟随重定向**：远程 HTTPS 网关可以把请求 302 到明文 HTTP 或另一台主机，Bearer Key 的边界由上游决定。现在与 `ai.rs` 一致，禁用重定向。
4. **模块边界门禁没进 CI**：`check:modules` 原来只在本地跑，CI 不执行。现在已加进 `.github/workflows/ci.yml`。

另外修正了 README / SECURITY 的过时口径：远程 HTTPS 模型网关是支持的，`workbench serve` 默认只听回环但 `--host` 可以扩大暴露面且没有鉴权。

## 仍然存在的风险与建议

### P0：发布前必须处理

- **历史安装包不能当最终包**。`workbench-release/` 里的 exe/deb/AppImage/dmg 生成于 2026-11-21 23:39，而最新提交是 2026-11-22 12:15，之后的助手、轮询、审计修复都没进包。必须从最新提交重新构建，并重算 `SHA256SUMS.txt`。
- **发布签名密钥**。Release workflow 的 `Verify assets` 要求 `.sig`；没有 `TAURI_SIGNING_PRIVATE_KEY` 时构建会停在签名/校验步骤。Windows/macOS 系统签名同理，没证书就只能明确发“未签名包”。
- **版本号拍板**。全仓目前是 `1.0.0`，但你的规范是 `0.0.x` 三段式。要发 1.0 就保留并在 CHANGELOG 固定；要遵守规范就统一改成 `0.0.1`，同时改 `package.json`、锁文件、`tauri.conf.json`、`Cargo.toml`、`Cargo.lock`，再跑 `npm run version:check`。
- **远端同步未闭环**。只有 `mirror` 是最新；`origin` 仍 403，Gitee/GitCode 缺凭据。发布前至少确认一个可写的 GitHub 远端和两个镜像。

### P1：真实数据口径与安全边界

- **`workbench serve --host` 的非回环绑定没有鉴权**。默认 `127.0.0.1` 是安全的，但显式绑 `0.0.0.0` 会把任务/项目数据和写接口暴露到局域网。建议二选一：直接移除 `--host`，或增加 `--allow-remote` + Bearer token，并让 `SECURITY.md` 的警告成为强制门禁。
- **CPU / 内存是“进程表逐项累加”口径**。CPU 合计超过 100% 是正常的（多核累加），但页面只写“CPU 合计”，用户容易误读；内存合计是各进程 RSS 相加，可能超过物理内存。建议把整机利用率单独采集（`System::global_cpu_usage()` + `used_memory()`），进程合计保留为第二指标；或者至少把文案改成“进程 CPU 合计 / 进程内存合计”。
- **助手配置 GET 返回明文 API Key**。桌面 WebView 和同源页面能读到；如果威胁模型包含本机恶意网页，建议后端返回掩码值，保存时用“是否修改”标记，或让聊天请求直接使用服务端已保存的配置，不把 Key 回传前端。
- **`cargo audit` 的 6 个 warning 已披露在 CHANGELOG 的 Known limitation**，发布说明里继续保持这句话，不要写成“零漏洞”。真正干净的升级路径是 Tauri 3 稳定后替换 GTK 栈。

### P2：可维护性，不阻断发布

- `Assistant.tsx` 1136 行，`check:modules` 已警告。建议拆成 `MessageMarkdown`、`ToolSteps`、`AssistantSettings`、`EmptyChat` 四个组件；同时复用 `src/pages/knowledge/MarkdownView.tsx`，能消掉当前 20 行 Markdown 渲染重复。
- 后端也有体积集中：`assistant.rs` 约 2460 行、`commands.rs` 1990 行、`server.rs` 1823 行、`cost_store.rs` 1736 行。可按“配置/传输/工具执行”和“路由/处理器/错误映射”拆，不必一次拆完。
- `check:modules` 现在只检查前端，且体量只是 warning。建议把 Rust 也纳入同一套规则，并让 CI 对“超过 1200 行”给出明确失败或至少 PR 注释。
- 根目录的空目录 `mac}` 是历史命令残留（未跟踪）；`AUDIT.md` 是 2026-10-12 快照。收尾时删掉空目录、给 `AUDIT.md` 加历史横幅，避免下一个人把旧结论当现状。

## 建议的收尾顺序

1. 拍板版本号，统一五处版本文件，跑 `npm run version:check`。
2. 从干净工作区跑一遍 `lint / format / check:modules / dup / coverage / build / clippy / fmt / cargo test / cargo audit / e2e`。
3. 提交并推送最新代码；确认 `mirror`、`origin`、Gitee、GitCode 至少各有一个可写远端。
4. 用 Release workflow 重新构建三平台安装包，配置 updater 签名；校验 `.sig` 与 `latest.json`。
5. 对最新安装包做一次“全新数据目录”烟测，再发 Release。

**一句话：代码可以收尾；发布包、版本号、签名和远端同步还没收尾。别把 `workbench-release/` 里的旧包直接发出去。**
